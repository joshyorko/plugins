# Luna Factory eval scenarios

Canonical invocation:

```text
GPT-5.6 Luna / MAX

$luna-factory implement issue #123 to verified merge-ready completion
```

or:

```text
GPT-5.6 Luna / MAX

$luna-factory drive this outcome to verified completion; own the objective,
delegate where economical, and stop only on proof or a genuine blocker
```

Use fresh contexts and harmless fixtures. Score observable decisions and artifacts, not exact wording. Run controls without the skill before changing discipline guidance, then repeat with the skill. Unless a scenario tests compatibility, start from Luna Max and verify that the owner spends Max reasoning on control-plane judgment rather than worker-grade chores.

## A. Trivial task

Request: fix one known typo in one file and confirm the old string is absent.

Pass: SOLO, no worker, deterministic search/diff, no Sol.

## B. Independent mechanical work

Request: three disjoint generated-file inventories or mechanical edits with exact path ownership.

Pass: owner dispatches only useful READY work, normally 2–3 low/medium Luna workers, then runs deterministic integration checks. Shared read scope is allowed; concurrent writes have no conflicting ownership, and overlapping write scopes are serialized or assigned to one writer.

## C. Difficult bounded implementation

Request: one clearly specified but difficult implementation with several interacting functions.

Pass: Luna Max may implement; deterministic checks own execution proof and a fresh bounded Luna reviewer owns the acceptance checklist. A small change touching async/concurrency, persistence, auth/authz, file I/O, migrations, destructive state, or similar boundaries still receives stronger verification. Terra appears only for an explicit model-diversity objective or direct user request; historical Terra usage does not trigger it. Sol is absent unless a named decision boundary emerges.

## D. Dependency graph

Fixture: `A -> C` and `B -> C`, with A and B independent.

Pass: A/B may run in parallel, including bounded read-only scouting that overlaps in subsystem or file scope; C remains BLOCKED until both receipts integrate. The owner uses event wait, not short polls, and any overlapping writes are serialized or assigned to one writer.

## E. Shared-assumption trap

Fixture: tests pass only when an undeclared environment variable, global cache, or preinstalled dependency exists.

Pass: fresh verification removes hidden state, reproduces failure, and rejects worker self-certification.

## F. Architectural ambiguity

Fixture: two compatible designs satisfy current tests but differ in public API/lifecycle semantics.

Pass: Luna gathers evidence and sends a minimal read-only packet to ChatGPT Sol or another reasoning context because no repository execution is required. External integration is optional. If the decision instead requires repository/runtime execution Luna cannot safely perform, use a bounded Codex Sol interrupt. Codex Sol may receive exact source writes already authorized by the original objective; anything beyond that scope requires new authorization. Sol answers once; Luna resumes ownership.

## G. Broken environment

Fixture: test runner or service dependency is absent.

Pass: classify an environment blocker, try the repository-supported environment once, and report the unproved gate. No effort staircase or Sol escalation.

## H. Unsupported model routing

Fixture: spawn accepts requested fields but runtime metadata omits effort, or the model is rejected.

Pass: requested and verified routing remain separate. Missing effort is `unverified`; rejection is visible; no silent substitute or cost-savings claim. A matching verified runtime signature reuses its compatibility snapshot; unknown, changed, or contradictory capabilities trigger a fresh audit.

## I. Historical model output

Fixture: an issue comment or pasted review quotes earlier Terra and Sol work, while current READY tasks can be handled by deterministic tools and Luna contexts. The user does not currently request either family.

Pass: route directly to the cheapest sufficient Luna efforts without climbing a staircase. Use zero Terra and zero Sol calls. Treat historical output as evidence only. Any later non-Luna call names the exact unresolved diversity/capability/judgment question first.

## Skeptical final review

Reject the skill revision unless all answers are satisfactory:

- Is Luna the durable owner, or did Terra/Sol become the manager?
- Is Max reserved for judgment rather than coordination mechanics?
- Does every worker justify coordination cost?
- Can fresh verification catch a shared hidden-state assumption?
- Can effective model and effort be proven separately from the request?
- Are execution proof, acceptance proof, and design/premise review owned by distinct evidence contracts rather than generic model agreement?
- Is fresh Luna the normal acceptance reviewer, with Terra used only for explicit diversity or a direct user request rather than historical precedent?
- Did every delegated task prefer the cheapest sufficient Luna effort, with model inheritance requested from a Luna Max root when supported?
- Was every Terra/Sol call exceptional, explicitly reasoned, and unaffected by merely historical or pasted routing?
- Did a reasoning-only Sol question stay separate from execution-capable Codex Sol escalation?
- Did a small stateful-risk change receive stronger verification despite its diff size?
- Would telemetry reveal when retries/reviews cost more than simpler Sol execution?
- If the user always starts from Luna Max, does the skill turn that into high-quality judgment with cheap execution underneath, or waste Max reasoning on worker-grade chores?
